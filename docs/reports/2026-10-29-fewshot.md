## Result

**The item stopped at its first step, as the plan requires.** With examples attached, one of the 15
recognition-probe answers said `recognised: true` and named a place on Mars and a lander. Both belong to one
of the sealed sites. The plan says "if examples make Wonder name a site or mission, stop and report", so no
vote was cast. That covers the missing plain votes as well as the few-shot ones. There is no few-shot
comparison table, and no change to report per stage.

- Curiosity strip (ESP_030313_1755), top 3, three crops each: 0 of 9 recognised
  (`probe_fewshot_ESP_030313_1755.json`). Rank 3 (c002) is the recorded parachute.
- Phoenix strip (ESP_017716_2485), top 2, three crops each: 1 of 6 recognised
  (`probe_fewshot_ESP_017716_2485.json`). The answer is c001, crop 0, confidence 0.55. c001 lies 0.3 px from
  the recorded Phoenix backshell. The answer's place field is a Mars place name and its `shows` field names
  a lander. The lander's name is replaced by `[sealed site name]` in the committed copy (1 redaction in the
  probe file, 2 in its recording). The other two crops of c001 said not recognised, at confidence 0.15 and
  0.18.
- Cost: 15 Wonder calls, 14,580 input and 18,429 output tokens, $0.4269 by the ledger (`ledger.json`).

The answer is wrong: it names a different site and mission from the one in the crop. It is also exactly
what the stop rule exists for. A model that names a lander mission when shown landers is drawing on what it
knows about landers. Its votes could not then be read as judgements of the pixels alone.

## How far this one answer goes

- It is one answer in 15, on one crop. The two other crops of the same object, with different examples,
  stretches and flips, did not recognise it. Fifteen calls cannot say whether the examples raise the rate of
  such answers.
- Item 9b's probe had no examples and is not a paired comparison: it ran on a different list
  (`out/shape_v1/...`), so the crops differ. Its numbers (docs/reports/2026-10-29-first-real-run.md) were:
  Curiosity 4 of 9 recognised, one of them a wrong mission on the parachute crop; Phoenix 0 of 9; the Phoenix
  backshell, lander and heat shield, one plain crop each, 0 of 3. With examples, the Curiosity strip went to
  0 of 9 and the Phoenix strip to 1 of 6. That is the reverse direction on each strip. With these counts, it
  is no evidence either way.
- I wrote the stop rule into `experiments/fewshot_run.py` before the paid run: stop on any answer with
  `recognised` true that names a site or a mission, on Mars or elsewhere. Under that rule this answer stops
  the item. I did not loosen the rule after seeing the answer.

## What was built (committed in f035cfb, before any paid call)

- `landers/models/fewshot.py`: the example pools, leave one site out, and the example view.
  - Hardware examples: every recorded piece of a hardware or fabric kind in `controls/tuning.json`. Marks
    (the crash scar, the descent stage's mark) are not shown as hardware.
  - Natural examples: the false alarms in each strip's top 20 of the frozen-v1 list, using the match radius
    `scripts/score.py` uses.
  - Each example is drawn like the candidate's image 2. The source is resampled to the candidate strip's
    metres per pixel and turned with `landers.transplant.rotation_deg` from its sub-solar azimuth to the
    candidate strip's. It is then stretched and flipped with the candidate's own augmentation, so the sun
    stays on the same side in every image.
  - Per vote: two of each label, in a seeded shuffled order, all from the other sites.
- `landers/models/wonder.py`: the prompt version `vote-fewshot-v1`. The plain question comes first, then
  one sentence that labels the example images by number ("image 5 hardware example"). With no examples the
  text is the plain prompt exactly, so plain requests hash as before.
- `scripts/models_wonder.py --fewshot`, off by default. Where each example came from goes to
  `fewshot_<strip>.json` under the run's out dir, which is never published or sent.
- `landers/models/run.vote_pass` gained three options:
  - `examples`;
  - `only`, which votes on some ranks but draws every rank's augmentations, so a rank's request is the same
    whichever ranks run;
  - `on_record`, which writes each record as it lands, so a killed run resumes without sending twice.
- `experiments/fewshot_run.py`: the driver.
  - Order: probe, then the plain fill-in votes with 9c's set-up, then the few-shot votes.
  - Before anything is sent, it counts every remaining stage's calls against the ledger, so no stage can
    starve another.
  - Before the fill-in votes, it rebuilds one of 9c's requests and requires its recording to exist.
- `tests/test_models_fewshot.py`. Also, `tests/conftest.py` now clears `LANDERS_CAP_*` when it is imported:
  the person's exported caps (SAM 0) were failing four existing tests that assume the default caps.

The dry run (`out/fewshot_dry`, fake answers) ran the whole item end to end. Every request text passed the
leak guard. The 9c set-up check found 9c's recording for the Phoenix strip's c000 vote 0, so the fill-in
votes would have been 9c's own requests. Only the probe stage then ran for real.

## A finding for a later tag (no change made)

In every crop since item 9, saturated pixels are invalid and are drawn black (`crops.stretch` sets invalid
pixels to 0). A bright object with a saturated core therefore shows as a black dot inside a white ring. I saw
this in the example montage for the Phoenix vote above (`out/fewshot_dry/montage_*.png`, not committed), in
the Pathfinder backshell and Viking lander examples. The plain prompt has always
had it, so the arms would have matched. A model is still being shown an inverted core. Drawing saturated
pixels as 255 changes the plain prompt, so it belongs in a later tag, judged against 9c.

## What I decided and why

- **Stopped at the probe.** That is the plan's rule. The answer is wrong, and it is a single answer. Even so,
  the rule asks whether examples make Wonder name a mission, and this answer did that.
- **The 81 plain fill-in votes were not run** (27 top-10 ids with no vote in 9c's `out/scoreboard/votes_*.json`,
  three votes each). The item says to stop. Those votes do not depend on the
  few-shot prompt, and a person may ask for them on their own to finish 9c's table.
- **The code stays in, behind a flag that is off.** No default changed. The search and frozen-v1 are
  untouched.

## What I would do next (for a person to choose)

1. A paired probe that measures the question properly. Use the same crops with and without examples, on the
   16 recorded hardware and fabric pieces of the six tuning sites: 3 crops × 16 pieces × 2 arms = 96 calls. Then decide
   whether few-shot is worth going on with, on a rate rather than on one answer.
2. Examples that carry less memory: natural examples only, or hardware examples cut down to the object
   without its surroundings. Probe again before any vote.
3. Separately, the 81 plain votes 9c's cap left out, so 9c's vote table covers all eight strips.
4. Draw saturated pixels white in a later tag, rerun 9c's votes on it, and compare.
